## 2 Теоретическая часть

### 2.1 Протокол HTTP

HTTP — текстовый протокол прикладного уровня, работающий по схеме «запрос — ответ». Запрос состоит из стартовой строки (метод, путь, версия) и заголовков; ответ — из строки состояния, заголовков и тела:

```
GET /index.html HTTP/1.1          HTTP/1.1 200 OK
Host: devops.local                Server: nginx/1.24.0 (Ubuntu)
User-Agent: curl/8.5.0            Content-Type: text/html
Accept: */*                       Content-Length: 312
```

Классы кодов состояния приведены в таблице 1.

Таблица 1. Классы кодов состояния HTTP

| Класс | Значение | Характерные коды |
|---|---|---|
| 2xx | Запрос успешно обработан | `200 OK` |
| 3xx | Перенаправление; новый адрес указан в заголовке `Location` | `301 Moved Permanently`, `302 Found` |
| 4xx | Ошибка на стороне клиента | `403 Forbidden`, `404 Not Found` |
| 5xx | Ошибка на стороне сервера | `500 Internal Server Error`, `502 Bad Gateway` |

Заголовок `Host` обязателен в HTTP/1.1: он позволяет размещать на одном IP-адресе любое число ресурсов, поскольку сервер выбирает конфигурацию по имени, указанному клиентом (источник [3]).

### 2.2 Веб-сервер Nginx

Главный процесс Nginx работает от имени `root`: читает конфигурацию, открывает порты 80 и 443 и загружает закрытый ключ TLS. Запросы обрабатывают рабочие процессы от имени непривилегированного пользователя `www-data`, поэтому ошибка в обработке запроса не даёт нарушителю привилегий `root`.

Таблица 2. Расположение файлов Nginx в Ubuntu

| Путь | Назначение |
|---|---|
| `/etc/nginx/nginx.conf` | Основной конфигурационный файл, подключающий остальные |
| `/etc/nginx/sites-available/` | Конфигурации всех ресурсов, в том числе отключённых |
| `/etc/nginx/sites-enabled/` | Символические ссылки на конфигурации активных ресурсов |
| `/var/www/` | Каталоги публикуемых файлов |
| `/var/log/nginx/` | Журналы запросов (`access.log`) и ошибок (`error.log`) |

Ресурс описывается блоком `server`; директива `server_name` сравнивается с заголовком `Host`. Если совпадения нет, запрос обрабатывает блок с пометкой `default_server`, а при её отсутствии — первый блок для данного порта.

Команда `systemctl reload nginx` применяет конфигурацию, не прерывая обслуживание: новые рабочие процессы запускаются, старые завершаются после обработки текущих запросов. При ошибке в конфигурации `reload` оставляет сервер работать со старой конфигурацией, тогда как `restart` его останавливает. Синтаксис проверяется командой `nginx -t` (источник [1]).

### 2.3 Протокол TLS

TLS обеспечивает шифрование, целостность и аутентификацию сервера. Аутентификация основана на сертификате — документе, связывающем открытый ключ с доменным именем и подписанном удостоверяющим центром (CA), корневой сертификат которого есть в хранилище клиента.

Самоподписанный сертификат обеспечивает шифрование и целостность, но не даёт автоматического доверия: клиенту нечем отличить сертификат владельца от сертификата нарушителя. Отсюда предупреждение браузера. Принять такой сертификат можно, получив его заранее по доверенному каналу и указав клиенту явно, что выполняется в задании 2.

Имя ресурса современные клиенты сверяют только с полем Subject Alternative Name (SAN); поле Common Name (CN) не учитывается. Сертификат Let's Encrypt для имени `devops.local` получить невозможно: удостоверяющий центр проверяет контроль над доменом обращением из сети Интернет, а учебный стенд извне недоступен (источник [7]).

### 2.4 Права доступа к публикуемым файлам

Пользователь `www-data` не является ни владельцем файлов ресурса, ни членом их группы, поэтому для него действуют права категории «остальные». Для файлов и каталогов одни и те же биты означают разное (таблица 3).

Таблица 3. Значение прав для файла и каталога

| Право | Для файла | Для каталога |
|---|---|---|
| `r` (4) | Чтение содержимого | Получение списка имён файлов |
| `w` (2) | Изменение содержимого | Создание, удаление и переименование файлов |
| `x` (1) | Запуск на выполнение | Переход в каталог и обращение к файлам по имени |

Чтобы прочитать файл, процессу нужно право `r` на файл и право `x` на каждый каталог пути от корня (источник [9]); права на всех компонентах пути выводит команда `namei -l`.

Для публикуемых файлов принята модель «владелец пишет, веб-сервер читает»: владелец — учётная запись деплоя `devops`, права `755` для каталогов и `644` для файлов. Если веб-сервер может изменять публикуемые файлы, уязвимость в приложении позволяет нарушителю подменить содержимое сайта. Закрытый ключ TLS защищается строже: права `600`, владелец `root`; его читает главный процесс до запуска рабочих.

При отказе в доступе Nginx возвращает код `403 Forbidden` и делает запись в журнале ошибок с системной ошибкой `(13: Permission denied)`. Формулировка зависит от того, где не хватило прав:

- на самом файле — `open() "/var/www/devops-site/index.html" failed (13: Permission denied)`;
- на каталоге пути — `"/var/www/devops-site/index.html" is forbidden (13: Permission denied)`.

Клиенту причина не сообщается, поэтому диагностика начинается с журнала ошибок.

### 2.5 Доставка содержимого средствами rsync

Утилита `rsync` передаёт только изменённые файлы и их изменённые части, а с флагом `--delete` удаляет в каталоге назначения файлы, которых нет в источнике. Используемые параметры приведены в таблице 4.

Таблица 4. Параметры утилиты rsync

| Параметр | Назначение |
|---|---|
| `-a` | Архивный режим: рекурсивно, с сохранением прав, времени изменения и символических ссылок |
| `-v` | Вывод списка передаваемых файлов |
| `-z` | Сжатие при передаче |
| `--delete` | Удаление в каталоге назначения файлов, которых нет в источнике |
| `--chmod=D755,F644` | Принудительная установка прав: `755` для каталогов, `644` для файлов |
| `--dry-run` | Вывод плана операций без их выполнения |

В архивном режиме права переносятся на сервер без изменений: файл с правами `600` станет недоступен веб-серверу, а файл с правами `666` или `777` — доступен ему для записи. Параметр `--chmod` приводит права на сервере к модели подраздела 2.4 независимо от прав в рабочей копии.

Завершающий символ `/` меняет смысл команды: `rsync site/ server:/dir/` копирует содержимое каталога `site` в `/dir`, а `rsync site server:/dir/` создаёт каталог `/dir/site`.

**Внимание.** Любую новую команду `rsync` с флагом `--delete` первый раз запускают с флагом `--dry-run`: ошибка в пути приводит к удалению данных на сервере.

Каждый запуск `rsync` через SSH открывает отдельное соединение. Правило `ufw limit`, настроенное в практической работе № 5 для порта 2222, блокирует источник, открывший шесть и более соединений за 30 секунд, поэтому сценарий деплоя должен открывать минимальное число соединений за запуск.

### 3.2 Рабочее окружение для rsync (выполняется до занятия)

Утилита `rsync` должна быть установлена и на сервере, и на хостовой системе (таблица 5).

Таблица 5. Подготовка хостовой системы

| Операционная система | Действие |
|---|---|
| Linux | `sudo apt install rsync` (как правило, уже установлена) |
| macOS | Входит в состав системы |
| Windows | В Git Bash утилита отсутствует; устанавливается WSL **версии 1** |

**Внимание.** WSL версии 2, которую `wsl --install` устанавливает по умолчанию, работает на гипервизоре Hyper-V. Как указано в подразделе 3.1 практической работы № 5, активный Hyper-V мешает работе VirtualBox или резко снижает её производительность. WSL версии 1 гипервизор не использует.

Установка WSL версии 1 (PowerShell от имени администратора):

```powershell
dism.exe /online /enable-feature /featurename:Microsoft-Windows-Subsystem-Linux /all /norestart
# перезагрузите компьютер
wsl --set-default-version 1
wsl --install -d Ubuntu
wsl -l -v          # в столбце VERSION должно быть 1
```

У WSL собственный домашний каталог, поэтому ключ и конфигурацию SSH необходимо перенести в него (клиент SSH отказывается использовать ключ с раздела `/mnt/c` из-за прав `777`):

```bash
mkdir -p ~/.ssh && chmod 700 ~/.ssh
cp /mnt/c/Users/<пользователь_Windows>/.ssh/devops_vm ~/.ssh/
cp /mnt/c/Users/<пользователь_Windows>/.ssh/config ~/.ssh/
chmod 600 ~/.ssh/devops_vm ~/.ssh/config
sudo apt update && sudo apt install -y rsync
ssh devops         # вход должен выполняться без запроса пароля
```

**Внимание.** Если репозиторий расположен на разделе `/mnt/c` и клонирован средствами Git для Windows, Git в WSL из-за прав `777` считает все файлы изменёнными (смена режима `100644 → 100755`), и проверка незафиксированных изменений в задании 4 будет срабатывать постоянно. Выполните в корне репозитория `git config core.fileMode false` и убедитесь, что `git status` не показывает изменений.

Далее команды, помеченные как выполняемые на хостовой системе, пользователи Windows выполняют в терминале WSL.

### 4.1 Задание 1. Установка Nginx и публикация ресурса

**Шаг 1.1.** `[VM]` Установите веб-сервер, проверьте состояние службы, прослушиваемые порты и пользователей процессов:

```bash
sudo apt update && sudo apt install -y nginx
systemctl status nginx --no-pager
sudo ss -tlnp | grep nginx           # ожидается 0.0.0.0:80
ps -o user,pid,ppid,cmd -C nginx     # master — root, worker — www-data
```

**Шаг 1.2.** `[VM]` Убедитесь, что порты 80 и 443 разрешены правилами из шага 3.1 практической работы № 5:

```bash
sudo ufw status verbose
sudo ufw app list
```

Пакет nginx регистрирует профили `Nginx HTTP`, `Nginx HTTPS` и `Nginx Full`, которые часто рекомендуются в руководствах. Выполнять `sudo ufw allow 'Nginx Full'` не нужно: правила для портов 80 и 443 уже существуют, а дубли усложняют аудит.

**Шаг 1.3.** `[Хост]` Проверьте доступность стандартного ресурса командой `curl -I http://devops.local` (ожидается `200 OK`) и откройте адрес в браузере.

**Шаг 1.4.** `[VM]` Создайте каталог ресурса с владельцем `devops` и временной страницей:

```bash
sudo mkdir -p /var/www/devops-site
sudo chown -R devops:devops /var/www/devops-site
echo "<h1>devops.local: placeholder</h1>" > /var/www/devops-site/index.html
```

**Шаг 1.5.** `[VM]` Изучите права на компонентах пути и проверьте возможности пользователя `www-data`:

```bash
namei -l /var/www/devops-site/index.html
sudo -u www-data cat /var/www/devops-site/index.html        # ожидается успех
sudo -u www-data touch /var/www/devops-site/test.html       # ожидается Permission denied
```

Объясните, почему `www-data` может читать файл, но не может создать новый.

**Шаг 1.6.** `[VM]` Создайте конфигурацию ресурса `/etc/nginx/sites-available/devops-site`:

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name devops.local;

    root /var/www/devops-site;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }

    error_page 404 /404.html;

    access_log /var/log/nginx/devops-site.access.log;
    error_log  /var/log/nginx/devops-site.error.log;
}
```

**Шаг 1.7.** `[VM]` Активируйте ресурс, отключите стандартный (удаляется ссылка, конфигурация сохраняется), проверьте синтаксис и примените конфигурацию:

```bash
sudo ln -s /etc/nginx/sites-available/devops-site /etc/nginx/sites-enabled/
sudo rm /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx
```

Если IPv6 на машине отключён, `nginx -t` завершится ошибкой `socket() [::]:80 failed (97: Address family not supported by protocol)`; в этом случае удалите строки `listen [::]:...` и повторите проверку.

**Шаг 1.8.** `[Хост]` Выполните `curl -i http://devops.local`; ожидается `200 OK` с текстом `devops.local: placeholder`.

**В отчёт:**
1. Вывод `ps` с пользователями главного и рабочих процессов.
2. Вывод команд шага 1.5 и объяснение.
3. Вывод `sudo nginx -t` и `curl -i http://devops.local`.
4. Окно браузера с опубликованным ресурсом.

### 4.2 Задание 2. Перевод ресурса на HTTPS

**Внимание.** Каждое изменение конфигурации применяется командой `sudo nginx -t && sudo systemctl reload nginx`. Ошибка в конфигурации при использовании `restart` делает недоступными все ресурсы сервера.

**Шаг 2.1.** `[VM]` Сформируйте закрытый ключ и самоподписанный сертификат:

```bash
sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout /etc/ssl/private/devops.key \
  -out /etc/ssl/certs/devops.crt \
  -subj "/CN=devops.local" \
  -addext "subjectAltName=DNS:devops.local"
```

Параметр `-x509` формирует сертификат, а не запрос на подпись в удостоверяющий центр; `-nodes` оставляет ключ незашифрованным, иначе пароль запрашивался бы при каждом запуске службы; `-subj` задаёт данные владельца без интерактивного ввода; `-addext` — поле SAN, по которому клиент проверяет имя ресурса. IP-адрес в SAN не включается: адрес в сегменте Host-only назначается по DHCP и может измениться.

**Шаг 2.2.** `[VM]` Сравните права на ключе и сертификате и проверьте доступ к ним от имени `www-data`:

```bash
sudo ls -l /etc/ssl/private/devops.key /etc/ssl/certs/devops.crt
sudo -u www-data cat /etc/ssl/certs/devops.crt  > /dev/null && echo "сертификат: доступен"
sudo -u www-data cat /etc/ssl/private/devops.key > /dev/null || echo "ключ: недоступен"
```

Ожидаются права `600` и владелец `root` для ключа, `644` для сертификата. Объясните, каким образом Nginx использует ключ, недоступный рабочим процессам.

**Внимание.** Закрытый ключ — секрет: копировать его за пределы `/etc/ssl/private` и добавлять в репозиторий не допускается. Сертификат является открытой частью ключевой пары и распространяется свободно.

**Шаг 2.3.** `[VM]` Приведите `/etc/nginx/sites-available/devops-site` к виду из двух блоков. В существующем блоке замените директивы `listen 80` на приведённые ниже строки для порта 443 и добавьте параметры сертификата; директивы `root`, `index`, `location`, `error_page` и журналы остаются без изменений. }

```nginx
# Блок 2: изменения в существующем блоке

    listen [::]:443 ssl;
```


Таблица 9. Требования к сценарию деплоя

| Номер | Требование |
|---|---|
| 1 | Запуск без аргументов выполняет доставку; запуск с аргументом `--dry-run` выводит план операций, не изменяя состояние сервера |

| 7 | Успешное завершение — код возврата 0 с выводом короткого хеша доставленного коммита |
| 8 | За один запуск сценарий открывает не более одного SSH-соединения (см. подраздел 2.5) |

Каркас сценария:

```bash
#!/usr/bin/env bash
# Доставка статического ресурса на devops-vm
# Использование: scripts/deploy.sh [--dry-run]
set -euo pipefail

REMOTE="devops"                     # псевдоним из ~/.ssh/config (ПР № 5, шаг 1.6)
REMOTE_DIR="/var/www/devops-site"
SITE_URL="https://devops.local"
CA_CERT="${HOME}/devops.crt"
LOCAL_DIR="$(git rev-parse --show-toplevel)/site/"

# 1. Разбор аргумента --dry-run
# 2. Проверки по требованиям 4 и 5
# 3. Синхронизация каталога ${LOCAL_DIR} на ${REMOTE}:${REMOTE_DIR}
# 4. При --dry-run — завершение с кодом 0 без проверки доступности
# 5. Проверка доступности ${SITE_URL} и завершение с корректным кодом возврата
```

Назначение параметра `set -euo pipefail`: `-e` — завершение при ненулевом коде возврата любой команды, `-u` — ошибка при обращении к необъявленной переменной, `-o pipefail` — ошибка любого элемента конвейера считается ошибкой конвейера. Работоспособность подтверждается пятью запусками (таблица 10). Для сценария 4 служба останавливается в отдельной SSH-сессии командой `sudo systemctl stop nginx` и после проверки запускается командой `sudo systemctl start nginx`. Код возврата выводится командой `echo $?` сразу после запуска.

| Номер | Условие | Код возврата | Ожидаемое поведение |

## 6 Факультативное задание. Атомарный деплой с возможностью отката

Задание выполняется по желанию и на оценку не влияет.

Сценарий задания 4 заменяет файлы непосредственно в каталоге ресурса: во время синхронизации клиент может получить частично обновлённый ресурс, а при ошибке в новой версии вернуться к предыдущей невозможно. Требуется переключать версии одной операцией и откатываться одной командой. Используется структура:

```
/var/www/devops-site/
├── releases/
│   ├── 20261005-143000/
│   └── 20261005-160500/
└── current -> releases/20261005-160500
```

Директива `root` указывает на `/var/www/devops-site/current`. Требования: каждый запуск создаёт каталог `releases/<дата-время>`; неизменённые файлы повторно не передаются (параметр `rsync --link-dest`); переключение выполняется последовательностью `ln -s <новая_версия> current_tmp && mv -T current_tmp current`; хранится не более пяти версий; запуск с параметром `--rollback` переключает `current` на предыдущую версию; права каталогов версий соответствуют модели подраздела 2.4; за один запуск открывается не более двух SSH-соединений.

Объясните, почему команда `ln -sfn` не обеспечивает атомарного переключения, а переименование командой `mv -T` обеспечивает.

## 8 Контрольные вопросы

1. Из каких элементов состоят HTTP-запрос и HTTP-ответ? Как Nginx выбирает блок `server` и какой блок обработает запрос, заголовок `Host` которого не совпадает ни с одной директивой `server_name`?
2. Чем различаются коды `301` и `302`? Обоснуйте выбор кода для перенаправления с HTTP на HTTPS.
3. Администратор изменил конфигурацию и выполнил `systemctl restart nginx`, после чего сервер перестал обслуживать все ресурсы. Определите нарушение процедуры и объясните, чем в этой ситуации `reload` отличается от `restart`.
4. Зачем конфигурации разделены на `sites-available` и `sites-enabled`? Как отключить ресурс, сохранив его конфигурацию?
5. Почему главный процесс работает от имени `root`, а рабочие — от имени `www-data`? Как Nginx использует ключ с правами `600` и владельцем `root`?
6. Какие задачи TLS решаются при использовании самоподписанного сертификата, а какая нет? Как в задании 2 обеспечено доверие к сертификату без обращения к удостоверяющему центру? Почему сертификат без поля SAN отклоняется браузером даже при совпадении CN с именем ресурса?
7. В конфигурацию добавлен заголовок HSTS со значением `max-age=31536000`, после чего сертификат сформирован повторно. Браузер отказывает в доступе без возможности продолжить. Объясните причину и укажите, на какой стороне устраняются последствия.
8. Доступ к серверу возможен только через проброс портов NAT: порт хоста 8443 → порт гостя 443, порт 8080 → порт 80. Куда директива `return 301 https://$host$request_uri` направит браузер при обращении к `http://localhost:8080`? Какое свойство сегмента Host-only устраняет проблему?
9. Файл `index.html` имеет права `644`, но ресурс возвращает `403 Forbidden`. Назовите причину, не связанную с правами самого файла, и укажите, какой командой проверить права на всех компонентах пути. Почему каталог с правами `711` позволяет отдавать файлы, а с правами `744` — нет?
10. Почему каталог ресурса принадлежит `devops`, а не `root` и не `www-data`? К каким последствиям привело бы право записи у `www-data`?
11. Выполнена команда `rsync -avz --delete site devops:/var/www/devops-site/`. Изменения на ресурсе не появились. Объясните, что сделала команда и какие файлы удалил бы флаг `--delete`.
12. Какую проблему решает параметр `--chmod`? Приведите два исхода доставки без него: нарушающий доступность ресурса и нарушающий его защищённость.
13. Сценарий деплоя открывал три SSH-соединения за запуск. После нескольких запусков подряд соединения стали отклоняться. Определите причину и предложите два способа устранения, не ослабляющих защиту сервера.
14. Каково назначение `set -euo pipefail` и `curl -f`? Почему сценарий, всегда завершающийся с кодом 0, непригоден для конвейера непрерывной интеграции?
