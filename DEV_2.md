## 📚 Теоретическая справка

### 1. Почему нельзя работать только в `main`?

Ветка `main` (или `master`) — это **продакшен-код**. Всё, что попадает в `main`, должно быть:
- протестировано,
- проверено коллегами (Code Review),
- готово к деплою.

Если вы коммитите напрямую в `main`:
- вы можете сломать сборку всем коллегам;
- невозможно откатить одну фичу, не откатывая другие;
- теряется история "что, зачем и когда" делалось.

**Правило DevOps-инженера:** `main` — священная корова. Никогда не коммитьте в неё напрямую.

### 2. GitHub Flow — простой и эффективный workflow

GitHub использует упрощённую модель ветвления (в отличие от тяжёлого Git Flow):

```
main ──────────●───────────────●────── (стабильный продакшен)
              ╱               ╱
feature-x ──●──●──●──PR──●──●   (ветка для конкретной задачи)
```

**Алгоритм:**
1. Создали ветку от `main` → дали ей понятное имя (`feature/add-auth`, `fix/login-bug`).
2. Работали в ней, делали коммиты.
3. Открыли Pull Request в `main`.
4. Коллеги проверили код (Code Review), оставили комментарии.
5. Исправили замечания.
6. Влили (merge) через GitHub.
7. Удалили feature-ветку.

📖 **Для изучения:** [GitHub Flow — официальная документация](https://docs.github.com/en/get-started/using-github/github-flow)

### 3. Альтернативы Git: почему SVN проиграл

| Характеристика | Git (распределённая) | SVN (централизованная) |
|---|---|---|
| Архитектура | У каждого своя полная копия репозитория | Один центральный сервер |
| Работа офлайн | Полноценная (коммиты, ветки, история) | Только локальные изменения |
| Ветвление | Мгновенно, дёшево | Копирование директорий, медленно |
| Скорость | Очень высокая | Зависит от сети |
| Merge | Умный, с отслеживанием истории | Ручной, часто с потерями |

**Вывод:** SVN ещё используется в legacy-проектах (особенно в госсекторе и банках), но **все новые проекты стартуют на Git**. Знание SVN полезно только для поддержания старых систем.

📖 **Для изучения:** [Git vs SVN — подробное сравнение (Хабр)](https://habr.com/ru/articles/525360/)

### 4. Git в терминале vs Git в IDE

**Терминал (CLI):**
- ✅ Полный контроль, все команды доступны.
- ✅ Скриптуемость (автоматизация через bash).
- ✅ Работает на любом сервере (SSH-подключение).
- ❌ Нужно помнить команды.

**IDE (VS Code, IntelliJ):**
- ✅ Визуализация истории, диффов, конфликтов.
- ✅ Быстрые действия через UI (commit, push, pull).
- ✅ Встроенный merge-конфликт редактор.
- ❌ Скрывает сложные операции (rebase, cherry-pick).

**Правило DevOps:** вы **обязаны** уметь работать в терминале. IDE — это удобная надстройка, но на сервере у вас будет только терминал.

## 💻 Практическая часть

### Задание 1. Работа с ветками в терминале

**Шаг 1.1.** Перейдите в ваш репозиторий `devops-course-2026`:

```bash
cd devops-course-2026
```

**Шаг 1.2.** Посмотрите, какие ветки есть локально и удалённо:

```bash
git branch          # локальные
git branch -r       # удалённые
git branch -a       # все
```

**Шаг 1.3.** Создайте новую ветку для "фичи" и переключитесь на неё:

```bash
git checkout -b feature/hobby-project
# или современный синтаксис:
git switch -c feature/hobby-project
```

**Шаг 1.4.** Убедитесь, что вы в новой ветке:

```bash
git branch
# Звёздочка * должна стоять рядом с feature/hobby-project
```

**Шаг 1.5.** Создайте файл `hobby.md` и заполните его:

```markdown
# Мой пет-проект

Идея: [опишите простую идею — телеграм-бот, сайт-визитка, скрипт для учёта расходов]
Стек: [Python / Node.js / Go / что угодно]
Цель: научиться [конкретная цель]
```

**Шаг 1.6.** Сделайте коммит **в этой ветке**:

```bash
git add hobby.md
git commit -m "feat: add hobby project description"
```

> 💡 Обратите внимание на префикс `feat:` — это соглашение **Conventional Commits**. Оно помогает автоматически генерировать changelog.

📖 **Документация:** [Conventional Commits](https://www.conventionalcommits.org/ru/)

✅ **Отчёт по заданию 1:** Скриншот вывода `git branch` и `git log --oneline --all --graph`.

### Задание 2. Pull Request и Code Review

**Шаг 2.1.** Отправьте вашу ветку на GitHub:

```bash
git push origin feature/hobby-project
```

**Шаг 2.2.** Откройте GitHub. Вы увидите жёлтую плашку **"Compare & pull request"**. Нажмите её. Если плашки нет — выберите ветку вручную в выпадающем списке рядом с "main ← ...".

**Шаг 2.3.** Заполните Pull Request:
- **Title:** `feat: add hobby project description`
- **Description:**
  ```
  ## Что сделано
  - Добавлено описание пет-проекта в hobby.md
  
  ## Зачем
  - Фиксация идеи для дальнейшей разработки
  
  ## Чек-лист
  - [x] Файл создан
  - [x] Сообщение коммита по Conventional Commits
  ```
- Нажмите **Create pull request**.

**Шаг 2.4.** **Code Review (парная работа).** Найдите соседа по парте (или преподаватель назначит вам ревьюера). Откройте его PR и оставьте **минимум один осмысленный комментарий** (не "LGTM", а например: "Может, добавить раздел 'сроки реализации'?").

**Шаг 2.5.** Получите комментарий на свой PR, исправьте (сделайте новый коммит в той же ветке, `git push` — PR обновится автоматически).

**Шаг 2.6.** После одобрения нажмите **Squash and merge** (об этом подробнее на следующем занятии, но сейчас используйте именно этот вариант). Удалите feature-ветку через GitHub.

📖 **Документация:** [GitHub Docs — О Pull Requests](https://docs.github.com/ru/pull-requests)

✅ **Отчёт по заданию 2:** Ссылка на смерженный PR и скриншот комментария от ревьюера.

### Задание 3. Git в VS Code

**Шаг 3.1.** Откройте ваш репозиторий в VS Code:

```bash
code .
```

**Шаг 3.2.** Изучите панель **Source Control** (иконка ветки слева, `Ctrl+Shift+G`):
- Посмотрите историю коммитов.
- Откройте diff файла `hobby.md` (клик по файлу в изменениях).
- Попробуйте сделать коммит через UI (введите сообщение, нажмите ✓).

**Шаг 3.3.** Установите расширение **GitLens** (если ещё не установлено) — оно показывает "кто и когда" редактировал каждую строку (git blame в визуальном виде).

**Шаг 3.4.** Создайте файл `ide_notes.md` и напишите 3 вещи, которые вам показались удобными в VS Code для работы с Git, и 1 вещь, которую удобнее делать в терминале.

**Шаг 3.5.** Закоммитьте и запушьте **через терминал** (не через UI!) — чтобы закрепить навык:

```bash
git add ide_notes.md
git commit -m "docs: add IDE vs CLI notes"
git push origin main
```

📖 **Документация:** [VS Code — Version Control](https://code.visualstudio.com/docs/sourcecontrol/overview)

✅ **Отчёт по заданию 3:** Скриншот панели Source Control с открытым diff и содержимое файла `ide_notes.md`.
