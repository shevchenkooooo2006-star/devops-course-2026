### 4.2 Задание 2. Конфигурация «приложение + Redis»

**Шаг 2.1.** `[Хост]` Создайте `docker-compose.yml`, удовлетворяющий требованиям таблицы 8.

Таблица 8. Требования к конфигурации

| Номер | Требование |
|---|---|
| 1 | Сервис `app` собирается из `Dockerfile` проекта в образ `kr2-app:1.0`. Сервис `redis` использует официальный образ Redis основной версии 7 на базе Alpine |
| 2 | Секрет `REDIS_PASSWORD` хранится только в файле `.env` на сервере и явно передаётся в окружение обоих контейнеров (через `env_file` или `environment`). Несекретные параметры заданы в `docker-compose.yml` |
| 3 | Приложение обращается к Redis по имени сервиса через изолированную пользовательскую сеть `backend` |
| 4 | Redis требует пароль и хранит данные в именованном томе `redis_data`, смонтированном в `/data` |
| 5 | Приложение запускается только после того, как Redis отвечает на команду `PING` |
| 6 | Порт приложения опубликован только на адресе `127.0.0.1`; порт Redis (6379) не опубликован |
| 7 | После перезагрузки сервера оба сервиса запускаются автоматически, если не были остановлены вручную |
| 8 | Процессы обоих контейнеров выполняются не от имени `root` |

Справочные фрагменты для сервиса `redis`:

```yaml
    command: ["redis-server", "--appendonly", "yes", "--requirepass", "${REDIS_PASSWORD:?REDIS_PASSWORD is not set}"]
    healthcheck:
      test: ["CMD-SHELL", "redis-cli -a \"$$REDIS_PASSWORD\" --no-auth-warning ping | grep -q PONG"]
      interval: 5s
      timeout: 3s
      retries: 5
```

Параметр `--appendonly yes` включает журналирование операций записи в файл AOF в каталоге `/data`. По умолчанию данные синхронизируются с диском раз в секунду, поэтому при внезапном отказе возможна потеря операций за последнюю секунду (источник [7]). Параметр `--requirepass` задаёт пароль.

Файл `.env` в каталоге проекта Compose использует только для подстановки выражений `${…}` в `docker-compose.yml`. В окружение контейнера переменные попадают лишь через `env_file` или `environment`. Значение для `${…}` берётся из переменной окружения оболочки, а при её отсутствии — из `.env` (источник [4]). Файл, указанный в `env_file`, читается напрямую, и окружение оболочки на него не влияет.

Поэтому результат подстановки и содержимое `env_file` могут разойтись. Пусть используются справочные фрагменты и `env_file: .env`, а в сессии выполнено `export REDIS_PASSWORD=…`. Тогда Redis запустится с паролем из оболочки, а приложение и проверка готовности получат пароль из файла, и аутентификация не пройдёт. Не экспортируйте эту переменную в рабочей сессии.

Выражение `$$…` раскрывает оболочка внутри контейнера при выполнении проверки.

Команда начинается с `redis-server`, чтобы скрипт точки входа официального образа выполнил предусмотренное понижение привилегий до пользователя `redis`. Запуск через `sh -c "redis-server …"` эту логику обходит, и Redis работает от `root` (источник [6]).

**Примечание.** После подстановки пароль становится аргументом команды контейнера и виден в выводе `docker compose config` и `docker inspect`. Он доступен любому, кто может управлять Docker; такие пользователи фактически имеют права `root` (ПР № 7, подраздел 3.1). Способ применяется в учебных целях. В промышленной эксплуатации секреты передаются специализированными механизмами, например секретами Compose или внешним хранилищем секретов.

```bash

for i in 1 2 3; do curl -s http://127.0.0.1:<порт>/; done

docker run --rm --user root kr2-app:1.0 find / -xdev -name .env   # пустой вывод
```

**Примечание.** Утилита `find` входит в базовую систему Debian и присутствует в образе `python:3.12-slim`. В других минимальных образах (например, `distroless`) её может не быть. Команда `find` проверяет итоговую файловую систему образа. Файл, скопированный в одном слое и удалённый в последующем, она не обнаружит, хотя он остаётся в образе (вопрос 3 раздела 7). Поэтому проверка частичная: отсутствие секрета в образе обеспечивается исключением `.env` из контекста сборки через `.dockerignore`, а не удалением в `Dockerfile`.

**Примечание.** Команда `ss` показывает прослушиваемый сокет процесса `docker-proxy`. При отключённом userland-proxy этого процесса нет и сокет не отображается. Источником сведений о публикации в этом случае служат `docker compose port` и `docker compose ps`.

### 4.4 Задание 4. Контроль и фиксация результата

**Шаг 4.1.** `[VM]` Убедитесь, что защита сервера не нарушена, и создайте снимок состояния `07-kr2`:

```bash
(cd ~/devops-course-2026 && scripts/audit.sh); echo $?          # 0
diff <(sudo ufw status numbered) ~/ufw-before-kr2.txt && echo "правила UFW не изменены"
sudo ls -l /etc/ssl/private/kr2.key ~/kr2/.env
# действующий пароль не встречается ни в одном доставленном файле, кроме .env;
# выводятся только имена файлов, сам пароль на экран не попадает
pw=$(sed -n 's/^REDIS_PASSWORD=//p' ~/kr2/.env)
if [ -z "$pw" ]; then echo "REDIS_PASSWORD не задан"
else grep -rlF --exclude=.env -- "$pw" ~/kr2; rc=$?
     case $rc in 0) echo "ПАРОЛЬ НАЙДЕН в перечисленных файлах";;
                 1) echo "пароль в файлах проекта не найден";;
                 *) echo "ошибка поиска";; esac
fi
unset pw rc
```

Порядок аргументов `grep` существенен: всё, что стоит после `--`, считается шаблоном или именем файла. Параметр `--exclude=.env`, записанный после `--`, перестаёт исключать `.env`, а `grep` завершается с кодом 2.


Эту часть закрывает проверка шага 4.1: она ищет само значение пароля во всех файлах, доставленных на сервер из этой ветки. Пароль шаблона в истории ветки `main` ожидаем (вопрос 2 раздела 7).

## 7 Вопросы к защите

1. Приложение в контейнере принимает соединения на адресе `127.0.0.1:<порт>`, порт опубликован как `127.0.0.1:<порт>:<порт>`. Почему обращение с сервера завершается ошибкой? Почему адрес `0.0.0.0` внутри контейнера не делает приложение доступным из сети?
2. Файл `.env` удалён из репозитория отдельным коммитом. Можно ли считать пароль из шаблона секретным? Что нужно сделать с паролем и что можно сделать с историей, учитывая, что ветка `main` уже опубликована (ПР № 3)?
3. Почему секрет нельзя удалить из образа, добавив в конец `Dockerfile` инструкцию `RUN rm .env`? Чем это опасно при публикации образа в реестр (ПР № 10)?
4. Почему `CMD` записывается в exec-форме? Как определить, какой процесс в контейнере имеет PID 1?
5. Кто и в какой момент подставляет значения `${REDIS_PASSWORD}` и `$$REDIS_PASSWORD` в `docker-compose.yml`? Что изменится, если в проверке готовности записать `${REDIS_PASSWORD}`?
6. Почему команда сервиса `redis` начинается с `redis-server`, а не с `sh -c "redis-server …"`? Как проверить, от имени какого пользователя работает Redis?
7. Порт Redis не опубликован. Зачем в таком случае пароль? Кто может обратиться к Redis?
8. Чем `depends_on` с условием `service_healthy` отличается от `depends_on` без условия? Что увидит пользователь в первые секунды после запуска при отсутствии условия?
9. Что произойдёт с данными после `docker compose down`, после `docker compose down -v` и после замены тега образа на `redis:latest`?
10. Зачем для `<имя>.devops.local` выпущен отдельный сертификат? Что выведет `curl --cacert ~/devops.crt https://<имя>.devops.local` и почему? Как Nginx выбирает сертификат, если на порту 443 описано несколько блоков `server`?
11. Какое значение выводится в строке `client` ответа `/whoami`? Почему приложение не может определить адрес клиента по TCP-соединению? Почему значению `X-Forwarded-For`, полученному напрямую от клиента, доверять нельзя?
12. Что произойдёт со всеми ресурсами стенда после `sudo reboot`? Какие службы и контейнеры запустятся автоматически, какие нет и почему?
13. Почему запись в файле `hosts` нужна на хостовой системе и не нужна на сервере для работы обратного прокси-сервера?
14. Порт приложения ошибочно опубликован как `"<порт>:<порт>"`. Почему UFW не препятствует доступу из сети? Обнаружит ли это проверка раздела `[5]` сценария аудита из ПР № 7? Какую проверку нужно добавить?
