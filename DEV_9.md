## 2 Теоретическая часть

### 2.1 CI и CD

Непрерывная интеграция (CI) предполагает автоматическую проверку каждого предлагаемого изменения. Непрерывная доставка или развёртывание (CD) переносит проверенный результат в целевую среду. Эти процессы связаны, но не тождественны.

В настоящей работе два независимых контура:

1. `CI — code quality` запускается для `push` в `main` и для Pull Request в `main`; он выполняет Pylint и ничего не публикует.
2. `Publish documentation` запускается только после изменения документации в `main`; он собирает и публикует сайт.

Поэтому зелёная проверка Pylint означает лишь соответствие Python-кода заданным правилам. Она не доказывает корректность ссылок в документации, работоспособность приложения или успешность будущего деплоя. Этот пробел обнаруживается в задании 4 и устраняется в самостоятельной работе.

### 2.2 Модель GitHub Actions

Workflow описывается YAML-файлом в каталоге `.github/workflows/`. Минимальная иерархия приведена в таблице 1.

Таблица 1. Основные элементы GitHub Actions

| Элемент | Назначение в настоящей работе |
|---|---|
| `on` | События запуска: `push`, `pull_request`, ручной `workflow_dispatch` |
| `permissions` | Права автоматически выданного `GITHUB_TOKEN` |
| `job` | Независимая единица выполнения на runner |
| `runs-on` | Образ runner; используется `ubuntu-latest` |
| `step` | Команда `run` или готовое действие `uses` |
| `environment` | Окружение `github-pages`, в котором фиксируется публикация и её URL |
| `concurrency` | Запрет одновременных публикаций одного сайта |

GitHub-hosted runner — временная виртуальная машина. После завершения задания её состояние не сохраняется. Следовательно, зависимости устанавливаются заново, а результат, необходимый другому заданию, передаётся через артефакт. Кэш зависимостей ускоряет повторные запуски, но не заменяет файл требований и не является хранилищем результата сборки.

Команда шага завершается кодом возврата. Нулевой код означает успех, ненулевой — отказ шага и, при отсутствии специальных исключений, всего задания. Параметр `continue-on-error: true` в работе не используется: он превратил бы обнаруженную ошибку в ложно успешную проверку.

### 2.3 События `push` и `pull_request`

Событие `push` возникает после появления новых коммитов в ветке. Событие `pull_request` относится к предлагаемому изменению и позволяет проверить результат до слияния. Фильтр `branches: [main]` для `pull_request` ограничивает целевую ветку, а не исходную.

Публикация в работе привязана только к `push` в `main`. Это исключает ситуацию, при которой любой ещё не рассмотренный Pull Request заменяет общедоступный сайт. Ручной триггер `workflow_dispatch` предусмотрен для повторной публикации без создания пустого коммита.

Фильтр `paths` у workflow публикации исключает лишнюю сборку при изменении только Python-кода. В обязательных проверках фильтры следует применять осторожно: пропущенная из-за фильтра required check может оставаться в состоянии ожидания и блокировать PR.

Обязательная проверка действует не только на кнопку merge. Пока для нового коммита не получен успешный результат required check, GitHub отклоняет и непосредственный `git push` в защищённую ветку (`GH013: Repository rule violations found` для ruleset, `GH006: Protected branch update failed` для классической защиты). Поэтому после включения правила `protect-main` в задании 2 все изменения, включая изменения workflow, вносятся только через ветку и Pull Request.

### 2.4 Pylint и статический анализ

Pylint исследует Python-код без его обычного выполнения: выявляет ошибки, неиспользуемые переменные и импорты, нарушения соглашений и потенциальные дефекты проектирования. Код возврата Pylint ненулевой при обнаружении сообщений включённых категорий, поэтому анализатор естественным образом останавливает шаг CI.

Параметр `--score=no` отключает только итоговую числовую оценку, но не сами диагностические сообщения и не ненулевой код возврата. Отключать правило, обнаружившее реальную ошибку, в задании запрещается: требуется исправить код.

Версии зависимостей зафиксированы в `requirements-dev.txt`. Это делает запуски воспроизводимыми: обновление инструмента не должно незаметно изменить правила проверки посреди курса.

### 2.5 MkDocs, артефакт и GitHub Pages

MkDocs преобразует Markdown-файлы из `docs/` в статический HTML-сайт. Команда:

```bash
mkdocs build --strict --site-dir site
```

создаёт каталог `site/`. Режим `--strict` превращает предупреждения, включая сообщения о ряде битых внутренних ссылок, в ошибку сборки. Каталог `site/` не хранится в Git: это производный результат, который должен быть воспроизведён из исходников.

Для публикации средствами GitHub Actions в настройках Pages выбирается источник **GitHub Actions**, а не ветка. Workflow выполняет четыре операции:

1. собирает сайт;
2. подготавливает Pages действием `actions/configure-pages`;
3. упаковывает именно содержимое `site/` действием `actions/upload-pages-artifact`;
4. публикует артефакт действием `actions/deploy-pages` в окружение `github-pages`.

Файл `index.html` должен находиться на верхнем уровне артефакта. Загрузка корня всего репозитория вместо каталога `site/` является ошибкой: исходные Markdown-файлы и служебные файлы не заменяют собранный сайт.

Если сборка новой версии завершилась ошибкой, задание `deploy` не запускается. Ранее опубликованная версия при этом сохраняется. Failed deployment не равнозначен автоматическому откату уже начавшейся публикации, но в сценарии настоящей работы отказ происходит до этапа `deploy`.

### 2.6 Права токена и параллельные деплои

GitHub автоматически создаёт для запуска `GITHUB_TOKEN`. Workflow запрашивает только необходимые права:

| Право | Назначение |
|---|---|
| `contents: read` | Прочитать содержимое репозитория для checkout |
| `pages: write` | Создать публикацию GitHub Pages |
| `id-token: write` | Получить OIDC-токен, необходимый действию `deploy-pages` для подтверждения публикации |

Права проверяются разными действиями и на разных этапах. `configure-pages` и `deploy-pages` обращаются к API Pages, поэтому им нужно `pages: write`. Кроме того, `deploy-pages` перед созданием публикации запрашивает OIDC-токен; без `id-token: write` переменные для его получения на runner не создаются, и шаг завершается ошибкой ещё до обращения к Pages. Одного `pages: write` поэтому недостаточно.

CI-проверке достаточно `contents: read`. Персональный токен доступа и пароль GitHub в workflow не используются.

Два одновременных деплоя могут завершиться не в порядке создания коммитов. Группа `concurrency: pages` упорядочивает публикации. Значение `cancel-in-progress: false` не обрывает уже начавшийся деплой; ожидается актуальный следующий запуск. Для CI допустима иная политика, но её следует выбирать осознанно.

### 4.2 Задание 2. CI, required check и инцидент с Pylint

#### 4.2.1 Первый workflow

**Шаг 2.1.** Оставаясь в `main`, создайте `.github/workflows/quality.yml`:

```yaml
name: CI — code quality

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  pylint:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v7

      - name: Setup Python
        uses: actions/setup-python@v7
        with:
          python-version: "3.12"
          cache: pip
          cache-dependency-path: requirements-dev.txt

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          python -m pip install -r requirements-dev.txt

      - name: Static analysis
        run: python -m pylint src/status.py --score=no
```

#### 4.2.2 Обязательная проверка

**Шаг 2.3.** После первого успешного запуска откройте **Settings → Rules → Rulesets** и создайте правило для ветки:

```yaml

    branches: [main]

      - "mkdocs.yml"
      - "requirements-dev.txt"
      - ".github/workflows/pages.yml"

permissions:
  contents: read
  pages: write

concurrency:
  group: pages
  cancel-in-progress: false

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v7

      - name: Setup Python
        uses: actions/setup-python@v7
        with:
          python-version: "3.12"
          cache: pip
          cache-dependency-path: requirements-dev.txt

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          python -m pip install -r requirements-dev.txt

      - name: Build documentation
        run: mkdocs build --strict --site-dir site

      - name: Configure Pages
        uses: actions/configure-pages@v6

      - name: Upload Pages artifact
        uses: actions/upload-pages-artifact@v5
        with:
          path: site

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}

    steps:
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v5
```

Связь `needs: build` гарантирует, что публикация начнётся только после успешной сборки и загрузки артефакта. Поле `environment.url` получает адрес сайта из выхода действия публикации.

## 7 Быстрая диагностика типовых затруднений

Таблица 4. Диагностический минимум

| Симптом | Вероятная причина | Что проверить в первую очередь |
|---|---|---|
| Workflow не появился в Actions | Неверный путь, расширение, ветка или YAML | `.github/workflows/`, push в `main`, отступы, вкладка Actions |
| CI не запустился для PR | Неверный триггер или целевая ветка | `pull_request.branches: [main]`, base ветку PR |
| Required check не выбирается в настройках | Проверка ещё ни разу не выполнялась | Сначала успешный запуск job `pylint` |
| Merge блокируется в ожидании проверки | Required check была отфильтрована или переименована | Фильтры `paths`, имя job, фактический статус в PR |
| `git push` в `main` отклонён с `GH013`/`GH006` и упоминанием `pylint` | Правило `protect-main` требует успешной проверки до обновления ветки | Ветка и PR вместо прямого push |
| `build` зелёный, `deploy`: `Ensure GITHUB_TOKEN has permission "id-token: write"` | Токену не выдано право на OIDC-токен | Блок `permissions`: `id-token: write` |
| `build` зелёный, `deploy` возвращает 403 | Недостаточны права токена на Pages | `pages: write`, источник Pages, ограничения организации |
| `deploy` ожидает артефакт | Не задана связь заданий или сборка не выполнилась | `needs: build`, успех upload |
| Pages показывает 404 после успеха | Неверный URL, неготов первый деплой, нет `index.html` наверху артефакта | Environment URL, `path: site`, содержимое сборки |
| Pylint зелёный, сайт не собирается | CI проверяет только Python | Журнал MkDocs; добавить docs check в PR |
| После исправления Re-run снова падает | Повторно запущен старый коммит | Новый push с исправлением, SHA запуска |
| Браузер показывает прежнее содержимое при зелёном deploy | Кэш либо проверяется не тот запуск | SHA/URL окружения, `build.txt`, обновление с обходом кэша |

## 8 Подготовка к практической работе № 10

а) изучить назначение модульных тестов и отличие тестового прогона от статического анализа;

б) подготовить устный ответ, почему последовательность «линтинг → тесты → сборка образа → публикация в реестр» не должна продолжаться после ненулевого кода возврата предыдущего этапа;

в) повторить понятия Docker image, tag и container registry из практической работы № 7;

г) изучить различие между артефактом GitHub Actions и опубликованным Docker-образом: оба являются результатами конвейера, но имеют разное назначение и жизненный цикл;

д) убедиться, что в репозитории отсутствуют токены и пароли; в следующей работе публикация в GitHub Container Registry будет выполняться с автоматическим `GITHUB_TOKEN` и правом `packages: write`, без персональных токенов и паролей реестра.

17. Почему после включения обязательной проверки `pylint` прямой `git push` в `main` отклоняется, хотя отдельный запрет push не настраивался? Как в этих условиях вносится исправление workflow?

## 10 Требования к содержанию и оформлению отчёта

Отчёт оформляется в формате Microsoft Word (.docx) и содержит титульный лист, цель и задачи работы, краткую схему CI/CD, материалы из блоков «В отчёт», выполненные в собственном репозитории, разборы трёх аудиторных инцидентов, результаты самостоятельной работы, ссылки на репозиторий, сайт и Pull Request, а также выводы.

Для каждого инцидента приводится пять элементов: симптом, доказательство из журнала, причина, исправление и проверка восстановления. Копии экранов должны позволять различить исходный отказ и последующий успешный запуск; желательно сохранить в кадре SHA коммита или номер запуска.

Перед сдачей убедитесь в выполнении условий таблицы 5.

Таблица 5. Условия, проверяемые перед сдачей отчёта

| Номер | Условие | Подтверждение |
|---|---|---|
| 1 | CI запускается для push в `main` и PR в `main` | Журналы двух типов событий |
| 2 | Pylint имеет только `contents: read`, проверка `pylint` обязательна | `quality.yml`, правило `protect-main` |
| 3 | Воспроизведён и исправлен `W0612` без отключения проверки | Красный и зелёный статусы одного PR |
| 4 | Pages использует источник GitHub Actions | Settings → Pages |
| 5 | Воспроизведён отказ deploy из-за прав и выполнено минимально необходимое исправление | Журнал `deploy` с требованием `id-token: write`, блок `permissions` |
| 6 | Сайт собран из `site/` и успешно опубликован | Зелёные `build` и `deploy`, URL сайта |
| 7 | Воспроизведён отказ MkDocs после merge; прежняя версия сохранилась | Failed build и страница версии 1 |
| 8 | Исправление ссылки опубликовало версию 2 | Успешный deploy и страница версии 2 |
| 9 | Сборка документации перенесена в CI для PR | Красный контрольный PR до merge и последующий зелёный |
| 10 | В Git не добавлены `site/`, `.env`, ключи и токены | `git status`, `git ls-files` |
| 11 | Итоговые workflow не содержат намеренно оставленных дефектов | Успешные последние запуски на `main` |
| 12 | После включения `protect-main` все изменения внесены через PR | История PR, отсутствие прямых коммитов в `main` после шага 2.3 |

Итоговый результат защиты: по любому из трёх инцидентов студент должен без подсказки показать отказавший шаг, объяснить причину и продемонстрировать, какое изменение восстановило работу.
