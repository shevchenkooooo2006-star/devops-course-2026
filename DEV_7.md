## 2 Теоретическая часть

### 2.1 Контейнер и виртуальная машина

Контейнер — процесс хостовой системы, изолированный средствами ядра Linux: пространства имён (namespaces) ограничивают видимость процессов, файловой системы и сети, контрольные группы (cgroups) — потребление ресурсов. Контейнеры используют ядро хоста, поэтому запускаются за секунды и не требуют отдельной ОС (таблица 1).

Таблица 1. Сравнение виртуальной машины и контейнера

| Признак | Виртуальная машина | Контейнер |
|---|---|---|
| Изоляция | Собственное ядро на гипервизоре | Общее ядро хоста, пространства имён |
| Размер | Гигабайты | Десятки–сотни мегабайт |
| Время запуска | Десятки секунд | Доли секунды — секунды |
| Пример в курсе | Ubuntu Server из практической работы № 5 | Приложение из настоящей работы |

### 2.2 Образ, контейнер, слой

Образ — неизменяемый шаблон, состоящий из слоёв; контейнер — запущенный экземпляр образа с собственным записываемым слоем. Слои создают инструкции `RUN`, `COPY` и `ADD` (таблица 2).

Таблица 2. Основные инструкции Dockerfile

| Инструкция | Назначение |
|---|---|
| `FROM` | Базовый образ |
| `WORKDIR` | Рабочий каталог для последующих инструкций и запущенного контейнера |
| `COPY` | Копирование файлов из контекста сборки в образ |
| `RUN` | Выполнение команды при сборке образа |
| `USER` | Пользователь, от имени которого выполняются последующие инструкции и процесс контейнера |
| `EXPOSE` | Документирование порта, прослушиваемого приложением; порт не публикуется |
| `CMD` | Команда, выполняемая при запуске контейнера |

При сборке Docker повторно использует слой из кэша, если инструкция и копируемые ею файлы не изменились. Изменение слоя делает недействительными все последующие слои (источник [2]). Поэтому редко изменяемые инструкции (установка зависимостей) размещаются выше часто изменяемых (копирование кода).

Команда `CMD` записывается в exec-форме (`["gunicorn", ...]`): процесс приложения получает PID 1 и сигнал `SIGTERM` при `docker stop`. В shell-форме PID 1 получает оболочка `/bin/sh -c`, которая может не передать сигнал приложению; по истечении 10 секунд контейнер завершается принудительно.

Файл `.dockerignore` исключает файлы из контекста сборки. Файл `.env` включается в него обязательно: иначе инструкция `COPY . .` поместит секреты в слой образа, откуда их может извлечь любой получивший образ.

### 2.3 Сети и тома

Docker Compose создаёт для проекта пользовательскую сеть типа `bridge`. Во встроенном DNS такой сети каждый сервис разрешается по имени: приложение обращается к СУБД по адресу `db`. Адрес `localhost` внутри контейнера указывает на сам контейнер, а не на хостовую систему.

Данные записываемого слоя удаляются вместе с контейнером. Для хранения данных СУБД используется именованный том — каталог, управляемый Docker независимо от жизненного цикла контейнеров. Команда `docker compose down` удаляет контейнеры и сеть, но сохраняет тома; `docker compose down -v` удаляет и тома (источник [5]).

### 2.4 Публикация портов и межсетевой экран

Публикация порта (`-p` или раздел `ports:`) реализуется правилами iptables, которые Docker добавляет в собственные цепочки. Пакеты, адресованные контейнеру, перенаправляются до обработки правилами UFW, поэтому порт, опубликованный на адресе `0.0.0.0`, доступен из сети независимо от политики UFW из практической работы № 5 (источник [6]).

Порт, предназначенный только для обратного прокси-сервера на той же машине, публикуется на адресе `127.0.0.1`: `127.0.0.1:5000:5000`. Порт СУБД не публикуется: приложение обращается к ней через сеть проекта.

### 2.5 Обратный прокси-сервер

Nginx принимает запрос по HTTPS, завершает TLS и передаёт запрос приложению по HTTP на адрес `127.0.0.1:5000` (директива `proxy_pass`, источник [8]). Исходные сведения о запросе передаются в заголовках `Host`, `X-Forwarded-For` и `X-Forwarded-Proto`. Если приложение не принимает соединение, Nginx возвращает клиенту `502 Bad Gateway` и делает запись в журнале ошибок.

```python
import os

import psycopg2
from flask import Flask

app = Flask(__name__)


def get_connection():
    return psycopg2.connect(
        host=os.getenv("DB_HOST", "localhost"),
        dbname=os.getenv("POSTGRES_DB", "app"),
        user=os.getenv("POSTGRES_USER", "app"),
        password=os.getenv("POSTGRES_PASSWORD", "app"),
    )


@app.route("/health")
def health():
    return "ok\n"


@app.route("/")
def index():
    conn = get_connection()
    try:
        with conn, conn.cursor() as cur:
            cur.execute(
                "CREATE TABLE IF NOT EXISTS visits ("
                "id SERIAL PRIMARY KEY, visited_at TIMESTAMP DEFAULT now())"
            )
            cur.execute("INSERT INTO visits DEFAULT VALUES")
            cur.execute("SELECT count(*) FROM visits")
            count = cur.fetchone()[0]
    finally:
        conn.close()
    return f"Hello from Docker! Visits: {count}\n"
```

```yaml
    image: postgres:16-alpine
    env_file: .env
    volumes:
      - db_data:/var/lib/postgresql/data
    networks:
      - backend
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]

      timeout: 3s
      retries: 5

    image: devops-app:1.0
    env_file: .env
    ports:
      - "127.0.0.1:5000:5000"
    depends_on:

    networks:
      - backend
    restart: unless-stopped

  db_data:

networks:
  backend:
```

```bash
cd ~/app && docker compose stop app
```

## 7 Контрольные вопросы

1. Какие механизмы ядра Linux обеспечивают изоляцию контейнера? Почему контейнер запускается быстрее виртуальной машины?

3. Приложение, запущенное командой `docker run`, получает отказ в соединении с СУБД по адресу `localhost`. Объясните причину. Каким образом приложение находит СУБД в конфигурации Compose?
